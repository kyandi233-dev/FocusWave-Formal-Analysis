# 协作角色、任务分工与 Git 治理

## 一、适用范围与权威位置

本说明规定“正式分析完整管线与报告证据库”以及关联分析代码仓库之间的协作边界、交付格式和版本控制规则。它服务于本地数据执行、网页 GPT 科学分析与写作、监督协调和专门 Git 操作四类任务。

本仓库是正式分析的证据索引与交付记录库，不复制对应代码仓库的源码，不提交原始数据和行级派生数据。可执行代码、环境文件和测试只在各自权威代码仓库维护；本仓库记录代码提交哈希、配置版本、输入输出索引、运行记录和报告可用的聚合证据。根目录 `README.md` 说明当前状态与模块入口，本文件是协作与 Git 治理的唯一权威。

## 二、四类角色及职责边界

| 角色 | 主要职责 | 输入 | 必须交付 | 禁止事项 |
|---|---|---|---|---|
| 本地数据执行任务 | 读取本地数据，按已批准的代码、配置和质量门运行或优化分析管线，生成标准化结果、产物索引和工程说明 | 权威代码仓库的已核验提交、冻结配置、只读原始数据、场次清单、字段结构和运行要求 | 标准化表/图/摘要、失败与不可评估记录、字段结构与校验值、实际命令和环境、待 Git 任务接收的变更清单 | 不自行改变科学定义，不从结果反推窗口/阈值/分组，不把探索性结果写成正式结论，不自行提交、`pull`、`push` 或修改其他仓库 |
| 网页 GPT 科学/写作任务 | 解释方法与结果，提出科学分析、统计方案和讨论文字，修改分析设计、方法说明和正式报告；需要代码时在对应权威代码仓库的独立分支开发 | 本仓库证据、运行记录、标准化聚合结果、字段字典、分析设计和用户明确的科学问题 | 科学解释、方案或文字修订、独立分支提交和合并请求（PR，代码审查请求）或待本地执行的明确任务单 | 不直接改 `main`，不绕过质量门解释未验证数据，不把网页环境当作本地原始数据执行环境，不在本仓库复制跨仓库源码 |
| 监督任务 | 负责分派、角色门控、基线核验、依赖协调、停止点判断、验收和跨任务回传；跟踪各仓库提交与产物关联 | 用户目标、各任务交付、仓库状态、运行记录、冲突和失败信息 | 分派说明、放行/停止判断、验收结论、跨仓库索引和未决问题 | 不替代本地任务做大批量运行，不代替网页 GPT 作深层科学推断，不绕过 Git 门控直接合并冲突 |
| 专门 Git 任务 | 维护本仓库和关联仓库的分支、工作树、fetch、提交、推送和提交台账 | 已验收的文件变更、运行记录、代码提交信息、远端基线和用户授权 | 清晰的中文提交、推送状态、提交哈希、远端核验和变更台账 | 不修改科学代码或分析定义，不代替数据执行，不删除历史，不 `reset` 用户工作，不强制推送 |

角色可以由同一个人工智能系统在不同任务中承担，但每次任务必须先声明当前角色和允许写入的位置。角色切换必须产生明确的交接信息，不得因为“顺手”而扩大修改范围。

### 角色协同的实际工作逻辑

本项目采用以下固定链路：**本地事实 → 网页代码/科学审查 → Git 隔离验收 → 本地最小复跑 → 监督门 → 全量生产 → 报告证据**。

- 网页 GPT 负责 GitHub 代码审查、科学方法审查和正式报告草拟；涉及代码时必须在对应权威仓库使用独立分支和 PR，不能直接修改 `main`。它不读取或假定本地原始数据事实，不能把未经过本地复跑的代码能力写成正式结果。
- 本地 Codex Luna 负责读取真实本地数据、按已批准提交进行最小复跑和全量生产，并交付产物说明、字段结构、失败明细和可复现命令。它不自行决定科学定义，不各自随意 `pull`、`push` 或提交，也不把具体身份映射复制到 Git 文档。
- 监督者负责事实冻结、任务拆分、依赖顺序、跨任务同步、返工判断和扩大门。监督者根据本地运行事实放行或停止后续任务，确认“输入可读”“工程运行完成”“质量门通过”“可进入正式分析/报告”之间不能互相替代。
- 专门 Git 任务负责独立 worktree、`fetch`、分支和提交基线核验、选择性暂存、中文提交、正常推送和提交台账；不代替本地任务运行数据，不代替网页 GPT 作科学推断。

身份协作也分两层：数据区保留 `identity_status` 的原始机器枚举及其历史运行元数据，Git 文档只说明聚合口径和解释规则，不改写 CSV。阶段 0.2 的解释层以 E2 姓名主匹配、手机号/学号精确交叉核验和 Q3 匿名键独立复核为依据；旧 R2 只作敏感性辅助，13 个 R2 外场次解释为当前队列单场分析组，不解释为完全未知，也不永久锁死为全球单例。当前口径是 44 个 session、38 个当前队列匿名分析组、6 个双场重复组（涉及 12 个 session）；具体匿名组键和完整 session 映射只留在 `D:\_AttentionData`，不写入本仓库文档或聚合表。未来约 72 个场次接入时必须全量重建映射。

## 三、任务输入、输出与交接

### 0. 统一启动顺序

任何多任务协作按以下顺序启动，不能直接从“想到一个任务”跳到分派：

1. 监督任务先直接进入已有网页版完整管线治理对话，读取其最新消息、目标分支、提交、测试和未决问题；不让本地子任务代为操控网页版，也不在已有对话未闭环时重复开启同类网页聊天。
2. 监督任务与网页版按“一问一答”逐项澄清科学定义、代码位置、输入输出、测试和验收。一个问题没有明确答复或证据时，不把含糊假设继续向下传递。
3. 网页版完成代码或文档提交后，专门 Git 同步任务核验并安全同步目标仓库、具体分支和完整提交到干净工作树，同时生成最新资料说明。具体执行任务不得依据网页口头总结或旧本地副本启动。
4. 监督任务以同步后的代码和资料形成完整任务包，明确仓库、分支、完整提交、样本、科学要求、允许改动、禁止事项、必需产物、逐项验收和停止点。
5. 具体本地执行任务只按任务包执行。不得自行创建临时脚本、临时身份表、临时输出合同或替代分支；确需新增长期入口时先回传设计和理由，等待批准。
6. 执行完成后先回传分支、完整提交、测试、真实试跑、产物和未决问题；监督任务验收后，再由专门 Git 任务处理提交/推送或向下一任务发放更新后的资料包。

并行任务数量以可监管为上限，不以“槽位可用”为理由同时开启多个网页对话。只有接口、输入和写入文件互不冲突，且每项都有独立验收标准时才并行。

### 1. 本地数据执行任务

开始前必须收到：权威代码仓库与分支/提交、实际解释器、配置文件及版本、输入数据根目录、样本和重复参与者规则、输出目录、质量门、停止点和是否允许批量运行。开始时先核验这些内容，并记录实际 `sys.executable`、输入表头、文件数量和必要校验值。

完成时交付：标准化结果和聚合图表的路径、字段结构、主键与单位、输入输出校验值、实际样本覆盖、缺失/拒绝/插值分轨、警告与失败、重试情况、可复现命令和建议的下一步。大规模运行应按场次或算法增量落盘，保留事件和失败记录，不批量写入不必要的原始图像副本。

### 2. 网页 GPT 科学/写作任务

开始前读取本仓库当前证据和分析设计，区分工程验证、探索性结果和正式结果。需要改代码时只在对应权威代码仓库建立独立分支，完成测试和合并请求；需要改报告时只使用已经通过报告准入门的证据，并把不适合报告或不可评估内容留在过程区。

完成时交付科学问题、使用的证据位置、假设和限制、修改文件、分支与提交、测试证据、待本地运行的命令和明确验收标准。没有本地数据证据时，不声称已完成正式分析或全样本结果。

### 3. 监督任务

监督任务必须亲自与已有网页版完整管线治理对话沟通，按一问一答把要求问清，再决定是否进入 Git 同步和本地执行；不得把未澄清问题交给本地子任务自行理解。它将大问题拆为网页代码/方法任务、Git 同步任务和本地数据执行任务，建立严格依赖顺序，维护停止点与未决问题。每个任务包必须包含具体仓库、分支、完整提交、资料版本、允许修改位置、禁止临时脚本、必需输出和逐项验收；不能假设执行任务已经知道完整项目背景。监督任务负责检查交付是否包含仓库基线、输入输出、样本边界和科学状态，但不把“文件生成”直接等同于“方法有效”或“结果可发表”。

### 4. 专门 Git 任务

Git 任务只处理版本与协作治理。提交前必须拿到待提交文件清单、变更原因、运行记录和验收证据；提交后必须回读提交差异、记录提交哈希，正常推送到目标远端，并再次核验远端提交和工作树。

## 四、并发与仓库隔离规则

1. 网页 GPT 不得直接修改 `main`。代码或配置变更使用独立分支和 PR；本地数据执行使用该分支的明确提交或经批准的稳定基线，不在执行过程中擅自切换分支。
2. 本地数据任务不得各自随意 `pull`、`push` 或提交。它们只在被授权的代码仓库中读取数据、运行管线、生成产物和写运行记录，完成后将变更交给监督任务和专门 Git 任务核验。
3. 每个任务开始前都要执行安全 `fetch` 并确认基线：实际路径、当前分支、HEAD、远端地址、远端目标分支、工作树状态和 ahead/behind。基线记录应进入任务回传或工作记录。
4. 任务执行期间若发现远端新增提交、其他任务未提交变化、同一文件被并发修改、输入字段变化或产物被覆盖风险，立即停止提交/合并，报告冲突对象和最后已知基线，等待监督任务重新分派。
5. 不使用 `reset --hard`、强制推送或其他覆盖历史的操作。不删除或重命名既有文件；历史错误和旧方案通过新增记录说明。需要清理时必须先获得用户明确同意并记录可恢复方式。
6. 关联代码仓库的源码修改保留在其权威仓库。本正式分析仓库只记录关联提交哈希、分支/PR、运行配置、产物路径和证据索引，不复制第二份脚本。
7. 网页端提交与本地工作树存在延迟时，具体执行任务必须暂停在旧提交；由专门 Git 同步任务完成快进或独立工作树更新、核验完整提交和资料变更后，监督任务再续发任务。
8. 不同时开启大量网页聊天。默认先复用并监管已有完整管线治理对话；只有任务边界互斥、资料已同步且验收责任明确时，才增加一个新的专项对话。
9. 本地执行对话不得因为入口不足而自行编写仓库外临时分析脚本。真实数据暴露缺陷时，应生成最小、匿名、可合成的失败样例并退回权威代码分支修复。

## 五、Git 提交、推送与台账门控

专门 Git 任务按以下顺序执行：

1. `fetch` 前记录当前分支、HEAD、远端和工作树；`fetch` 后再次确认远端没有新增提交。
2. 检查待提交差异，只纳入本任务明确范围内的新增或修改文件；发现无关变化、冲突或用户未提交工作时停止。
3. 核验 Markdown 相对链接、文件编号顺序、中文 UTF-8 编码、敏感数据边界、工作记录命名和 Git 差异。
4. 使用中文且范围清晰的提交信息，提交后记录哈希和文件清单。
5. 只在本地 `main` 与 `origin/main` 基线一致、工作树无未预期变化且验收通过时正常推送；推送后再次读取远端哈希和状态。

本仓库的提交台账至少包含：日期、任务名称、仓库、分支、提交前后基线、提交哈希、推送状态、关联代码仓库提交、运行记录路径、产物索引和未决问题。若远端有新提交或工作树不干净，台账记录“停止提交”，不能以合并冲突或本地覆盖方式强行完成。

## 六、科学与数据边界

- 场次不是独立被试；重复参与者必须按已核验映射在数据划分和模型评估中同折处理。
- 原始数据和行级敏感映射留在权威数据位置。本仓库只保存匿名键、聚合计数、字段结构、来源路径模板、校验值和必要的证据链接。
- 缺失、算法观测、算法拒绝和插值必须分轨。工程运行成功不代表检测质量、测量效度或科学结论成立。
- 不以显著性、图表美观或模型收敛作为唯一报告准入标准；不得为了结果漂亮改变预先约定的窗口、阈值、折或结局。
- 当前尚未通过验证的模态、指标或管线只能标为验证中、探索性、不可评估或受阻，不得在正式报告中写成已完成的全样本结论。

## 七、停止点与最小交接模板

出现以下任一情况必须停止并回传：仓库基线变化、工作树存在无法归属的修改、代码与产物提交不一致、字段结构变化、主键或时间轴无法解释、重复参与者身份冲突、质量门未通过、需要新增权限、需要删除/覆盖文件，或科学问题超出当前批准范围。

最小交接信息如下：

- 角色与任务编号；
- 实际仓库、路径、分支、HEAD、远端和工作树；
- 已核验的输入、配置、解释器和样本边界；
- 已完成的命令、测试、产物和校验值；
- 失败、不可评估、冲突和停止原因；
- 允许下一角色执行的动作、禁止动作和验收标准；
- 关联代码提交、PR 或本仓库运行记录路径。
