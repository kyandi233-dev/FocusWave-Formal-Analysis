# 6.3 1.16 系列单一 Formal 分支与代码任务治理

> 日期：2026-09-12  
> 最新修订：2026-09-12

为避免 1.16 系列随着专题增加不断产生独立 Formal 分支，当前治理规则冻结如下。

1. `FocusWave-Formal-Analysis` 的 1.16 系列唯一权威工作分支为 `codex/code-fix-ledger`。
2. `1.16.1`、`1.16.2`、`1.16.3` 及后续 `1.16.x` 方法、决策、实施计划均直接维护在该分支，不再为每个专题创建独立 Formal 分支。
3. 历史专题分支只作为 Git provenance（来源追踪），不再继续提交新内容。当前 `codex/1.16.1-supervised-interpretation-review` 与 `codex/code-fix-ledger` **并未处于同一提交**：Git 比较显示两者已经 diverged（分叉），`code-fix-ledger` 包含后续 1.16.3、README/导航与实现状态更新，而历史专题分支保留一个独立的 D4–D7 时间轨迹/问卷口径提交。相关实质内容已经在当前 `code-fix-ledger` 的 1.16.1 与总入口中收口，因此该历史分支不得继续作为当前方法入口，也不通过 force update（强制移动）伪造“同步”状态。
4. 当前 1.16 总状态入口为 `分析设计/1.16-当前方法总状态与执行入口_20260912.md`。专题文件负责具体科学合同，总入口负责当前跨模块状态、未决风险、执行依赖和真实数据放行门，README 只保留导航与高层状态，避免三处重复维护同一细节。
5. Formal 仓库负责研究问题、统计合同、参数冻结、代码修改计划和最终方法证据；实际代码实现、测试、CI（持续集成）和运行回报进入对应代码仓库 issue（议题）和实现分支。
6. 代码任务原则上采用“一个明确 issue 对应一个实现分支”，不得为了同一方法修改再拆出多个平行小分支，除非存在真实的互斥开发需求且在协作治理中预先登记。
7. 新 issue 可以先建立而不立即开分支。方法合同尚未审阅或实现基线尚未确定时，先保持 issue-only（仅议题）状态，避免产生空分支和废弃分支。
8. 任何实现发现需要修改科学规则时，先回到 `codex/code-fix-ledger` 更新相应 `1.16.x` 文档或 1.16 总入口，再继续代码；不得让临时代码实现反向覆盖 Formal 方法合同。
9. `1.15.x` 与更早文件保留历史方法演变和实现来源价值，但冲突处以 1.16 后出决策为准。不得在旧文档上继续追加当前状态以形成第二套活跃导航。
10. 代码/文档状态同步时必须区分：`implemented`（已实现）、`CI green`（专用持续集成通过）、`integrated`（已跨分支集成）、`real-data smoke validated`（真实数据冒烟验证完成）、`formal released`（正式放行）。这些状态不得互相替代。
