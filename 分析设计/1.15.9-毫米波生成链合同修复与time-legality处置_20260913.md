## 1. 已核实事实

本轮核对（2026-09-13，第二轮）：mmWave `main@3d3671f`、snapshot v1 corrected replay `source_commit@16729b2` 及其 manifest `source_hashes`、Formal `codex/code-fix-ledger@5ac28bd`；状态同步载体已改为 `codex/mmwave-state-sync-consolidated-20260913@980b60c`。首轮核对基线为 mmWave `main@7b68efe`、`codex/mmwave-formal-state-sync-v1@8f9bb62`。

当前 mmWave `main@3d3671f`（首轮核对于 `main@7b68efe`，两项均可见同一版本）的 `run_mmwave_probe_merge_ready_20260831.py` 仍存在三处合同问题：右端使用 `side="right"`；当前可见实现未按正式 DLL host receive/enqueue 时间与 `window_effective_start_unix_ms` 完成切片；`mmwave_hr_usable_window_fraction` 仍是 0/1 availability（可用性）标记而非真实比例。因此 current-main adapter 的生成链合同仍为 `OPEN`。

但 `MMWAVE_INTEGRATION_SNAPSHOT_V1_MANIFEST.json` 明确记录 snapshot v1 复用了 corrected DLL-time replay，source commit 为 `16729b2ef245f9304dae8674f3bac433bc02e98c`，时间合同为 DLL col1、`[window_effective_start_unix_ms, probe_onset_unix_ms)`、30 s、Block 起点截断。`2026-09-12_MMWAVE_HR_RECOVERY_P0_PIPELINE_LINEAGE_AUDIT.md` 又记录实际 B1 replay 使用两端 `side='left'`、DLL col1 和右开 probe 前窗口，并指出 exact `16729b2` 当时未进入 origin/main 祖先链。

**第二轮新核实的关键事实：`16729b2` 版本本身三项均已修复**（`win_start = row["window_effective_start_unix_ms"]`、两端 `side="left"`、`usable_window_fraction = course["signal_quality"]["usable_ratio"]`），因此 `main@3d3671f` 的可见 adapter（仅 `a97f8fa` 一次提交）与 snapshot v1 实际执行版本**不是同一份代码**。

但 snapshot v1 的 source-code provenance（源码来源追溯）**尚未闭环**：本地 replay `run_j/mmwave_probe_merge_ready_manifest.json` 的 `source_hashes` 记录了 adapter、producer、cohort runner 三个 sha256，而这三者与该 manifest 自身记录的 `source_commit=16729b2` 对应路径的实际提交内容**均不一致**（已核对 `scripts/` 下全部 blob；核对方自身以已知 adapter hash 自校验通过）。原因未定，可能是运行时存在未提交改动，也可能是 hash 计算方式不同；本裁决不对原因作结论。

因此必须区分：

- snapshot v1 的既有时间语义有持久 producer audit（生产端审计）证据，且没有证据表明其 2,320 行使用了错误窗口；
- 但该 replay 的执行源码无法从 `source_commit` 无歧义复现，source-code provenance 存在已核实的矛盾；
- 当前 main 可见 adapter 与该实际执行 lineage（执行链）同样尚未完成源码收口。

由此，`1.15.8` 中“snapshot v1 已被证明继承 current-main 三处缺陷”的表述不应继续作为既定事实。`1.15.8 = SUPERSEDED_BUT_TECHNICAL_ITEMS_NOT_CLOSED` 保持不变，但未关闭项应解释为 current-main 生成链合同与历史实际执行 lineage 尚未收口。

## 2. Q1：三处合同问题现在修

### 方法决定

三处问题保持 `OPEN`，应现在修复。该任务属于**生成链可追溯正确性与可复现性修复**，不属于已暂停的生理改进线；不得借此重启 C1/C2、重选 HR estimator（心率估计器）或形成 snapshot v2。

实现责任在 mmWave producer 维护侧；Formal 方法侧负责合同验收；Attention-Analysis 在上游未验收前继续 fail-closed（失败关闭），不自行猜测 producer 语义。

### 最低验收标准

1. 科学对齐只使用 DLL host receive/enqueue timestamp；Python processing timestamp 仅作 QC（质量控制）。
2. 窗口严格为 `[window_effective_start_unix_ms, probe_onset_unix_ms)`；恰好等于 probe onset 的帧必须排除。
3. `window_effective_start_unix_ms` 必须真正进入切片；Block 起点前帧必须排除，禁止跨 Block。
4. J/E 两批使用同一时间合同。
5. `mmwave_hr_usable_window_fraction` 不得继续以“fraction”名称承载 0/1 availability；若仅保留 0/1，应改为明确 flag，旧字段只能作为 deprecated（弃用）兼容字段；若保留 fraction 名称，则必须实现真实比例定义。
6. SOURCE_UNAVAILABLE、SOURCE_MALFORMED、QC failure 分层保留；不得补 0、静默删行，也不得升级 HRV 或 mmWave motion proxy（运动代理）的科学资格。

### 回归测试与 old-vs-new 证据

必须至少覆盖：右端边界合成测试、Block 截断、时钟源拒绝测试、J/E 一致性、字段语义、key/identity 守恒。

修复后必须在同一冻结输入上给出 old-vs-new 逐 probe 审计，至少包含：标准 probe key、old/new 实际入帧区间与 frame count、frame-membership 摘要、HR/BR/QC old/new 值与状态转移、不可用/损坏行保留情况、duplicate/missing/extra key。对 frame membership 完全相同的 probe，确定性派生量必须保持一致；否则必须单独解释。验收不得使用 Q1/Q2 或预测性能作为依据。

若用 governed cohort 验收，继续保持 116 sessions / 61 participant groups / 2320 probes 的键集合。该验收只证明生成链合同，不提升生理效度。

## 3. Q2：新增第五个 time-legality 状态

精确字符串：

`blocked_upstream_contract_mismatch`

定义：正式时间合同已经明确，但 upstream producer（上游生产端）实现或可追溯 lineage 与该合同存在已知不一致，或当前可执行主线无法无歧义复现已声明合同。

它不同于：

- `pending_upstream_freeze`：上游尚未冻结，但没有已确认合同冲突；
- `blocked_future_information`：已确认使用未来信息；
- `blocked_temporal_scope_unknown`：时间范围无法确定。

`blocked_upstream_contract_mismatch` 必须严格 fail-closed：所有正式预测资格和 device-package（设备组合）资格均为 false。只有同时完成上游合同修复、边界测试、old-vs-new 逐 probe 审计、**source-code provenance 闭环**并留下非空 evidence 后，才允许转为 `verified_pre_probe_only`。

对 mmWave 的放行边界（2026-09-13 第二轮收紧）：

- **snapshot v1 可用于接口、schema（数据结构）与 supporting integration（支持性集成）**：其时间语义有 corrected DLL-time replay 的生产端审计证据，且没有证据表明 2,320 行使用了错误窗口；
- **但在 source-code provenance 闭环前，当前任何 Cardiopulmonary（心肺）feature 都不得取得 `verified_pre_probe_only`，正式预测资格全部 fail-closed（失败关闭）。** 理由是 replay manifest 记录的源码 hash 与其自记 `source_commit` 对应文件不一致；该矛盾未澄清前，"evidence 精确指向 manifest、P0 audit、source commit/hash"不能作为充分条件；
- 由当前 `main@3d3671f` 可见旧 adapter 新生成的结果，一律标记 `blocked_upstream_contract_mismatch`，正式预测资格全部为 false。

## 4. Q3：Cardiopulmonary 报告边界

HR/BR 只能写为“毫米波设备推导的心率估计/呼吸率估计”“Cardiopulmonary（心肺）支持性指标”“`PHYSIOLOGY_LIMITED / SUPPORTING_ONLY`”。不得写成已完成生理效度验证、真实心率/呼吸率或独立金标准已验证结果。正式 cohort 从设计起没有独立 ECG（心电图）参考；snapshot v1 不得派生 HRV；mmWave motion proxy 不得写成已合格 Movement（动作）特征。

推荐方法措辞：

“毫米波设备用于非接触获得心率与呼吸率的设备推导估计。当前分析采用 `mmwave_integration_snapshot_v1` 作为接口基线，其分母、身份键和时间对齐已形成可审计的集成证据；但 HR/BR 的独立生理效度证据仍有限，因此仅作为 Cardiopulmonary 支持性指标解释，不作为已验证的生理真值。”

报告**不必一律写**“producer-side time-legality 未完全验证”。对既有 snapshot v1，更准确的限制是：时间窗口有 corrected DLL-time replay 的 producer 审计证据，但当前 canonical main 与该历史执行 lineage 的源码收口尚未完成。对 current-main 旧 adapter 新生成的结果，在修复前属于 `blocked_upstream_contract_mismatch`，不能进入正式预测。
