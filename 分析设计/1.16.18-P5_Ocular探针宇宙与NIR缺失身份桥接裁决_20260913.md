# 1.16.18 P5 Ocular 探针宇宙与 NIR 缺失身份桥接裁决（2026-09-13）

> 状态：`P5_IDENTITY_UNIVERSE_FROZEN / CODE_REPAIR_IN_VALIDATION`

## 1. 触发事实

P5 第一次真实接口运行暴露 Ocular 宽表缺少 canonical probe key（规范探针键）；第一次身份修复后再次真实物化时进一步发现，G1 `probe_measurement_candidates.csv` 只覆盖 2,180 个 probe，而 Ocular 宽表包含治理总体 2,320 个 probe。其差集为 140 个 probe，集中于 7 个场次，每场 20 个；这些 probe 在 RGB probe 表中存在，但不在 NIR G1 source universe（来源范围）中，且其 NIR predictor（预测变量）全部为缺失。

该现象属于模态 availability（可用性）差异，不属于 probe 身份冲突，也不意味着这 140 个治理 probe 应从研究总体删除。

## 2. 正式裁决：Ocular 保持 2,320 probe 治理宇宙

Ocular science-output（科学输出）的 probe universe（探针总体）保持正式治理样本的 61 名参与者、116 个场次、2,320 个 probe。不同 Ocular 信息来源允许在同一规范探针宇宙中具有不同 availability：

- NIR pupil（近红外瞳孔）只在具有合法 G1 来源和通过相应 QC（质量控制）的 probe 上产生有限值；
- RGB blink（可见光眨眼）按其真实 RGB 可用范围产生有限值；
- 缺失 NIR 的治理 probe 继续保留规范身份，其 NIR predictor 保持 missing（缺失），不得补零、插补或伪造；
- 后续 analysis-set（分析集合）按具体比较所需特征形成 comparison-specific complete cases（比较特异完整案例），而不是在 science-output 层提前全局删除缺某设备的 probe。

因此不采用“把 Ocular 收窄到 G1 的 2,180 probe”方案。该方案会把设备/模态缺失错误转化为样本不存在，并改变已经冻结的 Ocular 覆盖分母。也不允许保留 2,320 行但规范身份为空，因为 P5 要求 canonical probe key 完整且无冲突。

## 3. 身份来源与 fail-closed 规则

canonical probe key 固定为：

`participant_group_id + session_id + block_id + probe_index_in_block`

身份桥接采用多来源交叉校验，而不是把某一设备的科学测量值当作另一设备的数据来源：

1. G1 表为已有 NIR 候选的 probe 提供并验证规范身份；
2. 已纳入正式实验治理范围的完整 probe-level 表可为 G1 缺失 probe 提供**身份信息**；当前实现复用已进入 Ocular builder 的 RGB strict probe 表；
3. 两个来源重叠的 probe 必须在 session / participant group / block / probe index / `probe_event_id` 上一致，否则 fail-closed；
4. 补充身份来源只补 identity（身份），不得填充任何 NIR pupil predictor；
5. `probe_event_id` 保留为 provenance（来源追踪）字段，并与规范键逐行核对。

该规则实现的是“统一身份宇宙 + 模态特征按真实可用性缺失”，不改变任何已冻结的科学表示或测量阈值。

## 4. 对 P3/P5 的影响

P3 的科学冻结结论不变：hard `R_seg`、`level_mean`、`variability_mad`、20 s 最低时间跨度、early/late support、linear slope 与 quadratic curvature 均保持原决定；真实冻结覆盖硬核对仍应恢复为 slope 1857、curvature 1855。

P5 重新运行时应验证：

- Ocular 宽表 2,320 行均具有完整 canonical probe key；
- 2,180 个 G1 probe 与补充身份源在重叠范围完全一致；
- G1 缺失的 140 个 probe 不产生任何 NIR predictor 值；
- 三模态共同键与每个 registry-ready predictor 的有限值覆盖按真实 availability 计算；
- 不修改 unified feature registry（统一特征登记表），不运行 LOSO（留一参与者交叉验证）或监督学习。
